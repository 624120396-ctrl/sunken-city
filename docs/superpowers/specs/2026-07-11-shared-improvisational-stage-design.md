# 《沉没之城》共享即兴叙事舞台设计

> 状态：已确认产品方向，等待书面规格复核
>
> 日期：2026-07-11
>
> 路线：D - 共享即兴叙事舞台

## 1. 设计结论

《沉没之城》的房间主体验可以从“多人聊天附带跑团工具”演进为“多人共同操纵角色与场景的实时 AVG 舞台”。AVG 是表现语言，不是固定剧本；规则、骰点、玩家选择和随机事件继续决定故事。

D 路线复用既有视觉运行时研究，而不是另起一套无关系统：

- 使用 A 路线的背景、音频、立绘、转场、滤镜和降级策略。
- 使用 B 路线的 `SceneState`、权限投影、renderer 投影、事件记录和断线恢复边界。
- 吸收机会地图中的活场景引擎、可变表现层和多人调查画布。
- 将 B 的“KP 单向导演”扩展为“KP 控制全局、玩家控制自己角色”的共享即兴表演。

核心产品变化不是给聊天增加动画，而是把房间的主要交互从“发送消息”扩展为：

```text
参与者控制自己的角色表现
  + 发送对白或行动
  + 触发骰点与随机事件
  + 共同改变公开舞台
```

聊天记录继续承担权威历史和检索入口；舞台是当前房间状态的实时视觉投影。

## 2. 目标与非目标

### 2.1 目标

1. 让跑团全过程以实时 AVG 舞台呈现，而不是只在聊天列表中发生。
2. 保持临场发挥：不要求 KP 预先编写完整剧本、节拍或时间线。
3. 让 PL 自主控制自己角色的表情、动作、站位和登退场。
4. 让 KP 控制背景、BGM、环境、NPC 和全局舞台变化。
5. 支持玩家上传低门槛的多图片半身像变体包。
6. 保留现有房间日志、调查坞、线索板、NPC 档案、骰点和权限系统的权威性。
7. 支持断线恢复、角色权限投影、移动端和 reduced-motion 降级。

### 2.2 非目标

- 不把跑团改造成固定剧情 AVG。
- 不要求 `NarrativeBeat` 才能运行场景。
- 不加入 AI 自动导演、AI 表情推断或新的 AI 面板。
- 首期不支持 Live2D、Rive 角色、口型同步、骨骼动画或 3D 角色。
- 首期不实现完整时间线编辑器、动态光照、墙体视野、导航和战斗自动化。
- 不复制调查坞、线索板、NPC 档案或聊天日志的数据模型。
- 不把商业 FVTT/Roll20 素材放入公开静态目录。

## 3. 产品原则

### 3.1 即兴优先

舞台必须允许临时背景、默认剪影 NPC、无对白动作和即时随机事件。预设用于降低操作成本，不能成为开场前置条件。

### 3.2 自由表演，边界清晰

PL 可以直接控制自己的角色，但不能控制其他角色、NPC 或全局场景。KP 可以管理全局舞台和 NPC，并保留清场、纠错和临时锁定能力。

### 3.3 记录先于表现

消息、骰点、线索揭示和房间事件由现有业务系统记录。舞台渲染失败不能导致消息、骰点结果或正式揭示丢失。

### 3.4 同一事实，多种投影

桌面 Pixi 舞台、低功耗静态舞台、移动端简化舞台和纯 DOM 记录必须消费同一份服务端裁剪结果。

### 3.5 2D 是正式主体验

首期立绘舞台采用 2D，不是移动端降级。Three/R3F 保留给独立 3D 骰子、特殊场景和未来隔离演出。

## 4. 桌面房间结构

KP 和 PL 共用三栏骨架，组件位置稳定，但根据角色显示不同内容。

```text
┌──────────────┬────────────────────────────────┬──────────────────┐
│ 左侧身份栏   │ 中央共享 AVG 舞台              │ 右侧工具/记录栏  │
│ 220-280 px   │ minmax(0, 1fr)                 │ 300-360 px       │
│              │                                │                  │
│ 角色/成员    │ 背景、立绘、对白、事件演出     │ 上：角色工具     │
│ 状态/快捷项  │                                │ 或 KP 导演工具   │
│              │ 底部：输入与表现控制器         │ 下：聊天记录     │
└──────────────┴────────────────────────────────┴──────────────────┘
```

中央舞台获得最大面积。左右栏允许折叠，但不能把中央舞台挤压到无法容纳对话框和两名角色的宽度。

### 4.1 PL 左栏

- 当前角色半身头像与名称。
- HP、MP、SAN 和公开状态。
- 快捷技能。
- 房间成员、在线状态和当前登场状态。
- 角色档案入口。

### 4.2 KP 左栏

- 房间成员、角色绑定和连接状态。
- 当前登场角色与离场角色。
- KP 可见的私密状态提醒。
- 角色/NPC 快速定位。
- 当前场景和公开投影概览。

### 4.3 PL 右栏上部

- 快捷骰点和技能。
- 线索、笔记和角色档案入口。
- 自己的立绘包、表情、动作与登退场工具。
- 消息目标和私聊状态。

### 4.4 KP 右栏上部

- 场景切换、临时场景和背景选择。
- BGM、环境音和静音控制。
- NPC 登退场、立绘、表情和站位。
- 全局天气、滤镜、转场和舞台清理。
- 随机事件、骰点和现有调查工具入口。

### 4.5 右栏下部

保留完整聊天记录，包含：

- 公开对白和行动。
- 私聊和指定对象消息，按现有权限显示。
- 骰点结果。
- 系统事件。
- 可折叠的无对白舞台动作。
- 关键场景变化和恢复记录。

记录区域独立滚动。新消息不能因用户正在查看历史而强制跳到底部；应显示未读计数。

## 5. 中央 AVG 舞台

### 5.1 舞台层级

从后向前依次为：

1. 背景图。
2. 可选的环境层，如雾、雨、暗角和色调。
3. 后排角色与 NPC。
4. 前排角色与当前发言者。
5. 骰点、线索揭示和系统演出层。
6. AVG 对话框。
7. 输入与表现控制器。

### 5.2 自适应站位

舞台提供五个语义区域：`far-left`、`left`、`center`、`right`、`far-right`。玩家选择大致区域，系统负责：

- 避免完全遮挡。
- 根据登场数量统一缩放。
- 保留角色视觉锚点和脚底线。
- 在角色冲突时选择相邻空位。
- 当前发言者轻微前移、提亮或提高层级，不强制重新排列全场。

桌面端同时重点展示最多六名角色。超过六名的角色继续保持“已登场”状态，但进入后台列；玩家或 KP 可以将角色换入前台。移动端重点展示最多三名角色，其余角色以头像条表示。

玩家不能像自由画布一样逐像素拖拽，以避免多人同步抖动、遮挡和移动端构图失控。

### 5.3 对话框

对话框显示当前消息的：

- 角色名或发言身份。
- 对白或行动文本。
- 私聊/指定对象标识。
- 必要的骰点或状态关联。

较长内容允许展开，但舞台对话框只展示当前重点内容；完整文本始终进入右侧记录。

## 6. 共享控制规则

### 6.1 PL 权限

PL 可以立即执行：

- 自己角色登场或退场。
- 切换自己的表情和动作。
- 选择自己的语义站位。
- 发送带表演信息的对白或行动。
- 发送无对白快捷动作。

PL 不能：

- 操作其他 PL 的角色。
- 操作 NPC。
- 更换全局背景、BGM 或环境。
- 读取 KP 私密立绘、场景或标记。

### 6.2 KP 权限

KP 可以：

- 操作所有 NPC 和无主临时角色。
- 控制背景、BGM、环境和全局效果。
- 创建临时场景和默认剪影 NPC。
- 清理舞台、纠正冲突站位或让异常角色离场。
- 在秩序或故障场景下临时锁定角色舞台控制。

KP 不需要批准每次 PL 表演。临时锁定属于异常管理手段，而不是正常流程。

### 6.3 观察者

观察者只接收公开舞台投影和公开聊天记录，不能控制角色、背景或媒体。观察者不得通过舞台资源 URL 推断 KP 私密素材。

## 7. 输入与表演

### 7.1 带消息的表演

一次发送由以下可选内容组成：

```text
消息模式
+ 发送对象
+ 文本
+ portraitVariant
+ expression
+ action
+ preferredZone
+ enter/exit intent
```

未选择表现项时沿用角色当前舞台状态。缺失或失效的素材自动使用默认立绘，不能阻止文本发送。

### 7.2 无对白动作

首期提供受控动作集合：

- 点头、摇头、沉默。
- 靠近、后退、转身。
- 受惊、受伤、倒下。
- 登场、退场。

无对白动作产生舞台事件，并在聊天记录中形成可折叠的简化记录。它不生成普通聊天气泡，也不刷屏通知所有参与者。

### 7.3 私聊

私聊默认不改变公共舞台。若发送者选择表情或动作，它只投影给发送者和有权接收该私聊的对象；公共舞台保持原状态。

### 7.4 骰点与状态变化

骰点结果可以触发短暂的视觉反馈，并向玩家建议表情或动作。系统不能未经玩家确认永久切换其立绘状态。HP/SAN 等正式数值继续由现有房间系统权威管理。

## 8. 自定义立绘包

### 8.1 首期格式

每个角色可以绑定一个多图片立绘包：

- 必需：默认半身像。
- 可选表情：平静、喜悦、愤怒、恐惧、悲伤、怀疑、疯狂等。
- 可选动作：指向、抱臂、持物、受伤、倒下等。
- 自定义标签：用户可以增加自己的表情或动作名称。

支持 PNG 和 WebP 透明图片；JPEG 可以导入，但不能提供透明背景。上传源图建议最长边不超过 2048 px。系统应生成舞台代理图和缩略图，不在运行时直接加载超大原图。

### 8.2 上传流程

1. 选择或创建角色立绘包。
2. 上传默认立绘。
3. 批量上传其他图片。
4. 为每张图片指定表情、动作或自定义标签。
5. 调整裁切、安全区、脚底锚点和默认缩放。
6. 在标准舞台中预览。
7. 保存并绑定角色。

素材错误只影响对应变体。默认立绘有效时，角色仍可正常登场。

### 8.3 私有素材边界

- 玩家上传素材默认仅对相关房间和获授权用户可见。
- 私有原图和商业素材不进入 `apps/web/public`。
- 舞台只接收短期或受权资源引用，不暴露真实本地路径。
- 删除或失效素材时，历史事件保留标签和文本，但回放使用默认剪影。

## 9. 场景与媒体

KP 可以创建轻量场景预设，包含：

- 场景名称和公开描述。
- 背景图。
- BGM 和环境音。
- 默认色调、天气和转场。
- NPC 初始登场状态。

临时开场只要求名称和背景；其他字段均可为空。浏览器自动播放受限时，房间显示一次明确的“启用声音”操作，不能因音频失败阻止舞台进入。

首期支持静态背景与音频。循环视频背景、复杂 Shader 和后处理属于后续可选能力，必须经过性能验证后单独晋级。

## 10. 概念模型

本设计只定义产品职责，不提前确定数据库 schema。

### 10.1 `StageScene`

当前公开或私密场景的表现状态，包括背景、音频、环境参数和登场角色引用。它是 `SceneState` 的舞台子集，不拥有线索正文、NPC 档案或规则状态。

### 10.2 `StageActor`

角色或 NPC 在舞台中的投影引用，包括角色 ID、立绘包 ID、当前变体、语义站位、登场状态和可见受众。

### 10.3 `PortraitPack`

角色表现素材集合，包含默认立绘、变体标签、代理资源、锚点和缩放元数据。

### 10.4 `PerformanceIntent`

参与者提出的即时表演意图。服务端必须验证操作者、角色归属、房间能力、素材权限和预期舞台 revision。

### 10.5 `StageEvent`

验证通过后的舞台变化，包含事件 ID、幂等键、操作者、受众、目标 actor/scene、前后 revision 和必要的补偿信息。它作为 `TimelineEvent` 的 `stage` 类别记录。

### 10.6 `StageProjection`

服务端按 KP、PL、指定 PL 或观察者裁剪后的舞台数据。renderer 只能消费该投影，不能读取未裁剪的完整房间状态。

### 10.7 `StageSnapshot`

用于初次进入和断线恢复的当前舞台快照。历史事件用于审计和有限回看，不要求客户端从房间创建时重放全部事件。

## 11. 数据流与权威边界

### 11.1 即时舞台动作

```text
PL/KP 操作
  -> PerformanceIntent
  -> 服务端权限与 revision 校验
  -> StageEvent
  -> 更新 StageSnapshot
  -> 按角色生成 StageProjection
  -> Pixi/DOM renderer adapter
```

### 11.2 带消息的表演

文本消息与表演意图作为同一次用户操作提交。文本和正式房间事件优先持久化；素材变体失效时使用默认立绘完成舞台事件。renderer 故障不能撤销已经成功发送的消息。

### 11.3 权威归属

| 数据 | 权威层 |
| --- | --- |
| 聊天消息、骰点、线索、NPC 档案、HP/SAN | 现有房间/领域服务 |
| 角色控制权和可见性 | 服务端能力与角色投影 |
| 当前背景、音频、登场和立绘变体 | 舞台状态服务 |
| Pixi display object、纹理、滤镜 | 客户端临时渲染状态 |
| UI 抽屉、选中工具、输入草稿 | 本地 React 状态 |

Pixi 对象、DOM 节点和音频实例都不能成为房间真相。

## 12. 前端运行时边界

### 12.1 React/DOM

继续负责：

- 三栏房间结构。
- 角色卡、成员、工具和聊天记录。
- 输入框、表情/动作选择器和无障碍文本。
- 调查坞、线索板、NPC 档案和现有弹层。

### 12.2 PixiJS

中央 2D 舞台使用命令式 PixiJS runtime，由 React 组件负责创建、销毁和传入 `StageProjection`。当前项目仍是 React 18，因此首期不把要求 React 19 的 `@pixi/react` 作为默认集成层。

PixiJS 负责：

- 背景、立绘和层级。
- 自适应缩放、站位和转场。
- 天气、粒子和简单滤镜。
- 骰点和线索揭示的短时视觉反馈。

### 12.3 音频

BGM 和环境音使用独立音频控制层，消费舞台投影中的逻辑资产引用和音量状态。音频实例不放入 Pixi 状态，也不能阻塞舞台恢复。

### 12.4 Three/R3F

Three/R3F 不参与首期立绘舞台核心循环。未来特殊 3D 演出必须通过 renderer adapter 消费同一投影，并作为可移除视觉岛存在。

### 12.5 Worker 与 OffscreenCanvas

首期不预设必须启用 Worker 或 OffscreenCanvas。只有大地图、粒子、滤镜或解码 benchmark 证明主线程瓶颈后再引入，避免增加调试和浏览器兼容复杂度。

## 13. 错误处理与恢复

| 场景 | 行为 |
| --- | --- |
| 立绘变体缺失 | 使用角色默认立绘；保留原标签供修复 |
| 默认立绘也失效 | 使用系统剪影和角色名 |
| 背景加载失败 | 使用场景主题色和文字标题 |
| BGM 加载或自动播放失败 | 静默继续，显示启用/重试入口 |
| 重复舞台命令 | 依据幂等键忽略重复事件 |
| 过期 revision | 拒绝覆盖，返回最新快照后允许重试 |
| 玩家失去角色控制权 | 拒绝新的意图，当前舞台投影由服务端修正 |
| 断线重连 | 获取最新 StageSnapshot 和未读聊天，不全量重放 |
| Pixi context 丢失 | 显示 DOM 降级视图并尝试重建 renderer |
| 客户端性能不足 | 降低分辨率、停用粒子/滤镜/转场，保留立绘与对白 |

## 14. 移动端与无障碍

移动端使用舞台优先布局：

- 中央舞台成为主视图。
- 输入框固定底部。
- 左右栏变为互斥抽屉。
- 聊天记录变为底部上拉层，并保留未读计数。
- 快捷动作以有限按钮或菜单呈现，不显示复杂自由工具条。

无障碍要求：

- 所有立绘、表情和动作提供文本标签。
- 舞台变化同步生成可读事件文本。
- 键盘可以完成发送、选择表情、动作、站位和登退场。
- reduced-motion 停用位移动画、闪烁、视频背景和非必要粒子。
- 音频不是理解剧情的唯一通道。
- 纯 DOM 降级仍能完成全部跑团操作。

## 15. 性能与资源预算假设

以下是首期验证门槛，不是未经测试的承诺：

- 桌面重点角色上限：6；移动端：3。
- 每个角色只保留当前变体和相邻候选的热纹理。
- 离场角色纹理可释放或降为缩略图缓存。
- 背景、立绘代理图和音频按场景预加载，不能预载整个战役素材库。
- 低功耗模式关闭视频、粒子、模糊和复杂滤镜。
- 舞台代码与素材必须路由级懒加载，不能增加非房间页面首屏成本。

具体帧率、内存、包体和释放阈值由既有最小验证方案确定，不在设计阶段伪造结论。

## 16. 首期交付范围

### Phase D1：共享静态舞台

- 三栏 KP/PL 房间骨架。
- PixiJS 静态背景与透明立绘。
- 多图片立绘包上传、标签、锚点和代理图。
- 五区自适应站位。
- 玩家控制自己的表情、动作和登退场。
- 带消息表演与无对白动作。
- 右侧权威聊天记录。
- StageEvent、权限投影、快照和断线恢复。
- 移动端抽屉及 reduced-motion/低功耗降级。

### Phase D2：场景与声音

- KP 场景预设和临时场景。
- BGM、环境音和浏览器声音授权流程。
- NPC 立绘包和快速剪影。
- 简单天气、滤镜和转场。
- 骰点与线索揭示的短时演出。

### Phase D3：经验证后的增强

- 循环视频背景。
- 更丰富的粒子和 Shader。
- 特殊 Three/R3F 演出岛。
- 有限回看和战役记忆呈现。

D2、D3 不自动进入首期实施计划，必须分别通过产品价值和性能验证。

## 17. 验证与测试策略

### 17.1 产品验证

1. 四名 PL 和一名 KP 能否在没有预制剧本的情况下完成十分钟即兴场景。
2. PL 能否在不打断输入的情况下选择表情、动作和站位。
3. KP 能否在数秒内切换背景、BGM、NPC 和临时事件。
4. 右侧记录能否准确解释舞台上发生过的关键变化。
5. 舞台是否改善玩家理解和参与，而不是增加操作负担。

### 17.2 权限验证

- PL 不能操作其他角色或 NPC。
- 观察者不能发送舞台意图。
- 私聊表演不泄漏到公共舞台。
- KP 私密素材和真实 URL 不进入 PL 投影。
- 角色解绑、离房和权限变化会立即撤销控制能力。

### 17.3 状态验证

- 重复命令不产生重复动作。
- 过期命令不能覆盖新状态。
- 消息发送成功但素材失败时仍保留消息。
- 断线重连恢复相同的背景、角色、表情和站位。
- renderer 重建不改变服务端舞台状态。

### 17.4 视觉与性能验证

- 1、3、6 名角色的桌面构图。
- 1、3 名角色的移动端构图。
- 超长角色名、长对白和自定义动作标签。
- reduced-motion、低功耗和 WebGL context 恢复。
- 立绘包切换、场景切换和离房后的纹理/音频释放。

除非用户另行明确要求，验证阶段不执行深度测试，也不接入生产数据或公开商业素材。

## 18. 验收标准

D1 只有在以下条件全部满足时才算成功：

1. KP、PL、观察者看到正确的角色投影和工具。
2. PL 可以即时控制自己的角色，但不能控制其他对象。
3. 舞台支持无剧本临时开场、临时 NPC 和随机事件。
4. 表情、动作和站位可以随消息发送，也可以作为无对白动作发生。
5. 消息、骰点、线索和角色数值仍由现有系统权威管理。
6. 断线重连可以恢复当前舞台。
7. Pixi renderer 失败时，用户仍可通过 DOM 记录和输入继续跑团。
8. 移动端、reduced-motion 和低功耗模式仍能完成核心流程。
9. 私聊、KP 私密素材和角色控制权不存在跨角色泄漏。
10. 未引入 Live2D、AI 自动导演、完整时间线或其他首期非目标。

## 19. 与既有研究的后续关系

D 路线不废弃 A/B/C：

- A 继续定义可选的电影化表现能力。
- B 继续提供事件、角色投影和恢复的架构基础。
- C 继续观察完整 3D、WebGPU、XR 和重型编辑器。
- D 成为面向实际房间体验的共享即兴产品路线。

后续实施仍应拆分为两个边界清晰的线程：

1. VTT/房间运行时线程：共享舞台状态、权限、事件、Pixi renderer 和房间集成。
2. 全站视觉系统线程：Three/R3F、Motion、视觉 profile、素材代理和跨页面依赖治理。

本规格只定义 D 路线产品设计。用户书面复核通过后，才进入独立实施计划。
