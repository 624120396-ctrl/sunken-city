# 沉没之城 UI/UX 产品设计总方案

**日期：** 2026-07-04  
**适用项目：** 沉没之城 / Sunken City  
**适用范围：** 信息架构、用户流程、线框图、视觉系统、image2 资产约束、样板页、前端 UI/UX 重构路线。  
**使用对象：** 用户用自然语言指挥 Codex；Codex 查阅、拆任务、修订、执行。  

---

## 1. 方案定位

本方案不是企业团队流程文档，也不是单纯视觉稿说明。

它的作用是把《沉没之城》的 UI/UX 重构从“逐页打补丁”改成一套可持续执行的产品设计系统：

1. 先明确信息架构。
2. 再明确核心用户流程。
3. 再画低保真线框。
4. 再约束 image2 生成的纹理和背景。
5. 再做高保真样板页。
6. 最后推广到真实页面和组件。

核心目标：让《沉没之城》看起来更精致、华丽、自然、明亮，同时仍然适合长期跑团、阅读、管理和移动端使用。

### 2.1 产品是什么

《沉没之城》是围绕《克苏鲁的呼唤》跑团体验构建的 Web 平台。

它要同时承载：

- 角色卡。
- 房间。
- 聊天。
- 骰点。
- 战斗。
- 结算。
- 报告。
- 论坛。
- 个人资料。
- 黑水港。
- 溺者之牌。
- 无名集市。
- 位阶与印记。

产品气质不是普通后台、工具表单或恐怖海报，而是“更明亮的深海秘仪档案馆”。

### 2.2 视觉方向

已确认方向：

- 更明亮。
- 深海冷雾。
- 秘仪档案馆。
- 明亮档案纸。
- 浅色湿石。
- 氧化铜。
- 克制旧金。
- 少量血红只用于危险语义。
- 非纯黑克苏鲁。
- 减少 AI 味儿。

明确避免：

- 全局黑幕。
- 泛用黑色透明卡片。
- 灰底灰字。
- 低透明金色正文。
- 大面积血红恐怖背景。
- 纯概念海报式 UI。
- 移动端把 PC 侧栏直接堆叠。

### 2.3 交互复杂度

本轮不是静态展示，而是服务真实产品的渐进式 UI/UX 重构：

- IA 和用户流程要完整。
- 线框图先低保真。
- image2 资产必须服务 UI。
- 高保真样板页先做一个。
- 前端实现逐步推进。
- 默认只做轻量验收，不主动深度测试。

## 3. 方案路线选择

### 方案 A：直接生成高保真图，再照图改页面

优点：

- 见效快。
- 用户容易判断视觉方向。

缺点：

- 容易得到漂亮但不可执行的海报式 UI。
- 房间页、移动端和长期模块仍然会散。
- image2 资产可能和真实组件尺寸不匹配。

结论：只适合早期方向探索，不适合作为接下来的主路线。

### 方案 B：先设计系统，再逐页替换

优点：

- 能减少黑色透明卡片。
- 能建立 Surface、token、纹理资产的统一规则。

缺点：

- 如果没有 IA 和流程，系统会变成“好看的组件库”，但页面体验仍可能混乱。
- 房间页、黑水港、溺者之牌这类复杂页面仍缺结构约束。

结论：可作为中间阶段，但不能跳过 IA 和线框。

### 方案 C：IA + 用户流程 + 线框图 + image2 资产 + 样板页

优点：

- 先解决产品结构，再解决视觉。
- image2 生成有明确用途，不会变成随机素材。
- 可以兼顾 PC/KP、移动端/PL、观察者、长期玩家。
- 适合 Codex 分阶段执行。

缺点：

- 前期文档量更大。
- 需要先接受低保真结构，不急于改页面。

结论：推荐采用。后续所有 UI/UX 工作都以方案 C 为主线。

### 4.2 导航分组建议

主导航不应按技术目录堆砌，应按玩家心智分组：

| 导航组 | 包含页面 | 设计意图 |
| --- | --- | --- |
| 跑团 | 故事书、房间、骰点历史、报告 | 用户进行游戏的主入口 |
| 调查员 | 角色列表、角色详情、创建角色、成长 | 像档案柜，不像数据表 |

| 秘仪 | 黑水港、溺者之牌、位阶、印记 | 游戏化和长期目标 |

### 4.3 页面优先级

P0：

1. 信息架构与线框图。
2. image2 资产规格。
3. 样板页：首页 / 故事书。
4. Surface 材质系统。

P1：

1. 个人资料 / 调查员档案夹。
2. 无名集市。
3. 论坛。
4. 黑水港。
5. 溺者之牌。
6. 位阶 / 印记。

排序理由：

- 个人资料是长期留存的聚合页，适合先建立“档案夹”心智。
- 无名集市适合验证遗物、材质和收藏陈列。
- 论坛适合验证长文阅读和文献归档。
- 黑水港与溺者之牌玩法性更强，应在线框和材质稳定后再做。
- 位阶 / 印记依赖长期身份感，适合作为后续强化层。

P2：

1. 房间页结构拆分。
2. PC/KP 工作台。
3. 移动端/PL 参与端。
4. OBSERVER 只读端。
5. 房间报告档案化。

冻结：

1. 后台 / admin。
2. 结团后的正式角色成长机制。
3. 房间后端业务规则重写。
4. Socket 事件格式变更。

## 5. 核心用户流程

### 5.1 KP 跑团流程

```text
登录
→ 进入故事书 / 房间列表
→ 创建房间
→ 邀请或等待 PL 加入
→ 检查成员与角色绑定
→ 开场
→ 推进场景
→ 管理聊天 / 骰点 / 线索 / NPC / 战斗 / 私聊
→ 暂停或继续
→ 进入结算
→ 保存每位调查员结算草案
→ 确认结算
→ 结团写回
→ 查看报告
```

设计重点：

- PC 上信息密度可以高，但必须分区清楚。
- KP 的工具不能和聊天主舞台混在一起。
- 结算入口必须在生命周期上明确，不应像普通按钮一样弱化。
- 危险操作需要更强确认和血红语义。

### 5.2 PL 移动端参与流程

```text
登录
→ 进入邀请链接或房间列表
→ 加入房间
→ 绑定角色卡
→ 等待开场
→ 查看聊天和骰点
→ 查看自己的角色状态
→ 执行公开发言 / 公开骰
→ 根据权限查看私聊或提示
→ 结算阶段查看自己的结算
→ 结团后查看报告
```

设计重点：

- 手机首屏优先显示聊天、骰点、自己状态。
- KP 工具、成员列表、日志、设置不应挤占主任务。
- 底部操作区要稳定，不能因为消息数量变化跳动。
- PL 不应该看到会误导其权限的按钮。

### 5.3 OBSERVER 观看流程

```text
进入房间
→ 识别自己是观察者
→ 阅读公开聊天 / 公开骰 / 房间公开状态
→ 查看允许公开的内容
→ 无法操作战斗、结算、私聊、KP 工具
```

设计重点：

- 观察者身份必须明显。
- 只读不是残缺态，而是低干扰观看态。
- 禁用按钮不如隐藏无权限操作，避免误导。

### 5.4 长期玩家留存流程

```text
登录
→ 查看个人档案
→ 查看调查员档案
→ 回看已结团报告
→ 进入论坛阅读或发帖
→ 查看位阶 / 印记 / 收藏
→ 进入无名集市
→ 游玩黑水港或溺者之牌
→ 获得新的记录、收藏或故事记忆
```

设计重点：

- 长期模块要像档案馆，不像普通工具页。
- 收藏、印记、位阶要有“被保存”的感觉。
- 黑水港和溺者之牌要有可重复进入的玩法循环。

### 5.5 当前规则和跑团模式边界

当前默认：

- 规则系统以 CoC7 为主。
- 用户默认具备基础 CoC 跑团知识，产品不承担完整规则教学。
- 当前房间体验以实时文字跑团为主。
- 语音团辅助、异步团、CoC6、Pulp Cthulhu、多规则系统暂不纳入本轮。

这些方向不是永久否定，而是为了防止 UI/UX 重构期间扩大范围。

### 5.6 需要后续细化的异常流程

以下流程暂不阻塞 Phase 0，但进入房间页重构前应补充：

- 断线重连后，聊天、骰点、生命周期和成员状态如何恢复。
- 房间满员或角色绑定失败时，PL 看到什么。
- KP 改变成员身份或移除成员时，PL / OBSERVER 页面如何提示。
- 房间从 `IN_PROGRESS` 进入 `PAUSED`、`FINISHING`、`COMPLETED`、`CANCELED` 时，正在输入或打开 sheet 的用户看到什么。
- 秘密骰、私聊、KP 笔记在不同身份下的可见性边界。

```text
│ 用户身份区：头像 / 名称 / 位阶 / 印记        │
├──────────────┬───────────────────────────┤
│ 档案目录       │ 主档案页                    │
│              │ 最近角色                    │
│ 角色          │ 跑团报告                    │
│ 报告          │ 收藏与遗物                  │
│ 收藏          │ 论坛记录                    │
│ 印记          │                            │
└──────────────┴───────────────────────────┘
```

体验目标：

- 像档案夹，不像个人设置页。
- 角色、报告、收藏、印记要互相呼应。
- 移动端改为分段 tabs。

## 7. 视觉系统方案

### 7.1 色彩语义

| 语义 | 用途 | 约束 |
| --- | --- | --- |
| 明亮档案纸 | 正文、阅读、主内容 | 不发灰，不低对比 |
| 浅色湿石 | 主工作区、页面底板 | 保持清爽，不像水泥灰 |
| 深海青黑 | 侧栏、工具台、背景深层 | 非纯黑，不大面积压暗 |
| 氧化铜 | 导航、边框、结构线 | 克制使用，不做全文颜色 |
| 旧金 | 仪式感、重点标记 | 不用于低透明正文 |
| 血红 | 危险、战斗、理智崩坏、不可逆操作 | 少量、高语义、不可做大背景 |

### 7.2 Surface 材质

建议扩展：

- `archive`：档案纸，正文阅读。
- `limestone`：浅色湿石，主工作台。
- `basalt`：暗釉石材，工具台。
- `copper`：氧化铜，边框与导航。
- `relic`：遗物陈列，高价值模块。

组件原则：

- `variant` 解决层级。
- `material` 解决材质。
- `tone` 解决语义。
- 纹理只通过 token 或组件 API 引用。

### 7.3 布局密度

PC：

- 1440px 不能过度紧凑。
- 2560x1080 不能空，也不能把内容无限拉宽。
- 复杂页面可使用三栏，但每栏职责必须清楚。

移动端：

- 375px 不横向溢出。
- 主任务先出现，次要工具进入 sheet。
- 不把多个大卡片上下贴成连续黑条。

## 8. image2 资产约束

### 8.1 生成前必须有资产规格卡

每张图生成前必须写清：

| 字段 | 内容 |
| --- | --- |
| 资产名 | 例如 `archive-paper-light` |
| 用途 | 正文 Surface / 背景 / 边框 / 装饰 |
| 尺寸 | 例如 1024x1024、2048x1024 |
| 明度 | 明亮 / 中性 / 深色 |
| 对比度 | 低干扰 / 中等 / 强强调 |
| 可平铺 | 是 / 否 |
| 允许细节 | 纸纤维、微水痕、氧化铜细纹 |
| 禁止内容 | 字母、符号、脸、怪物、强图案、强中心构图 |
| 入库路径 | `apps/web/public/ui-textures/` |
| CSS token | 例如 `--sc-texture-archive-paper` |

### 8.2 首批资产

| 资产 | 用途 | 要求 |
| --- | --- | --- |
| 明亮档案纸 | 正文、卡片、报告 | 纸纤维细，不能发黄过度 |
| 浅色湿石 | 主工作区底板 | 明亮、冷调、低干扰 |
| 氧化铜边框 | 导航、分隔、仪式线 | 可切片，不能太脏 |
| 深海冷雾 | 页面背景 | 低对比，不抢正文 |
| 暗釉石材 | KP 工具台、暗面板 | 非纯黑，有质感 |
| 旧金箔细纹 | 高价值状态、印记 | 细线，不铺满大面积 |

### 8.3 image2 提示词原则

详细 Prompt as Code 结构、通用禁止项和 6 张首批纹理的完整提示词，以 `docs/superpowers/plans/2026-07-04-sunken-city-ui-asset-pipeline.zh-CN.md` 为准。本文只保留设计原则。

所有实际提交给 image2 的 prompt 必须使用自然、原生英文；中文只用于规格说明、验收说明和用户沟通。

提示词必须强调：

- UI texture。
- subtle。
- readable。
- low contrast detail。
- no text。
- no logo。
- no characters。
- no central object。
- seamless 或 edge-friendly。
- bright enough for Chinese UI readability。

提示词不得强调：

- cinematic poster。
- horror splash art。
- dramatic monster。
- dark black glass card。
- red blood background。
- complex symbol wall。

### 8.4 入库原则

生成图不能直接进页面。

流程：

```text
资产规格卡
→ image2 候选
→ 人工筛选
→ 压缩
→ 命名
→ 入库
→ token 登记
→ Surface 或页面引用
→ 轻量截图确认
```

不得提交：

- `outputs/`。
- 未压缩大图。
- 未登记临时素材。
- 页面里直接写死临时图片路径。

## 9. 前端落地策略

### 9.1 先做设计系统，不先碰房间后端

优先文件方向：

- `apps/web/src/components/system/Surface.tsx`
- `apps/web/src/components/system/PageShell.tsx`
- `apps/web/src/styles/tokens-v2.css`
- `apps/web/src/styles/system-v2.css`
- `apps/web/src/styles/background-v2.css`

目标：

- 给 Surface 增加材质表达。
- 给 CSS token 增加纹理引用。
- 让页面不再依赖黑色透明卡片表达高级感。

### 9.2 现有系统组件 API 索引

后续扩展材质系统时，应优先兼容现有组件 API，再小步新增字段。

| 组件 | 当前核心 props | 当前职责 | 材质化建议 |
| --- | --- | --- | --- |
| `Surface` | `variant`、`tone`、`density`、`padding`、`interactive` | 所有新 Surface 的基础容器 | 增加 `material`，保留现有 `variant` 和 `tone` 语义 |
| `PageShell` | `eyebrow`、`title`、`description`、`actions`、`aside`、`layout`、`contentClassName` | 页面标题、说明、操作区、主体和侧栏 | 允许 header 和 body 继承页面级材质背景 |
| `ReadablePanel` | `eyebrow`、`title`、`description`、`actions`、`tone` | 长文阅读或说明性内容 | 默认适配 `archive` 材质 |
| `ActionCard` | `eyebrow`、`title`、`description`、`icon`、`media`、`meta`、`actions`、`tone` | 可点击入口卡片 | 根据模块选择 `archive`、`limestone`、`relic` |
| `DataCard` | `label`、`value`、`detail`、`icon`、`tone` | 状态数字、摘要数据 | 保持紧凑，避免纹理影响数字识别 |

注意：

- 不要一次性重写组件 API。
- 先让 `Surface` 支持材质，再逐步让其他组件受益。
- 若新增 `material`，应保留默认值，避免旧页面大面积改动。

### 9.3 样板页优先

第一个样板页建议二选一：

1. 首页 / Dashboard：能最快体现整体气质。
2. 故事书 / 房间列表：更贴近跑团核心。

推荐先做“故事书 / 房间列表”，原因：

- 与跑团核心强相关。
- 不直接碰复杂房间逻辑。
- 能验证导航、档案纸、房间卡、状态、移动端和超宽屏。

### 9.4 房间页后置但提前规划

房间页不能继续逐页补丁，应该按结构拆：

- `RoomShell`：页面骨架、身份、生命周期、响应式布局。
- `RoomStage`：场景、聊天、骰点、主输入区。
- `RoomParticipantRail`：成员、角色绑定、观察者、状态。
- `KpWorkbench`：KP 工具分区。
- `PlayerConsole`：PL 的移动端和桌面参与区。
- `ObserverConsole`：只读观看状态。

注意：

- 不改后端房间规则。
- 不改 Socket 事件格式。
- 不改骰点算法。
- 不改战斗规则。
- 不改私聊数据流。

## 10. 响应式规则

### 10.1 桌面

1440px：

- 主内容清楚。
- 侧栏不挤压正文。
- 卡片间距比旧版更舒展。

1920px：

- 可以出现三栏结构。
- 右侧工具台可以常驻。

2560x1080：

- 不能只把 1440px 内容居中留大空白。
- 可以增加辅助信息栏、状态栏或横向内容密度。
- 主阅读宽度仍要受控，避免长行难读。

### 10.2 移动端

375px：

- 无横向溢出。
- 不堆两个连续大黑卡。
- 主 CTA 和输入区稳定。

430px：

- 可以显示更多状态摘要。
- 工具仍进入 sheet，不直接铺满。

移动端交互补充：

- 触摸目标建议不小于 48px x 48px。
- 聊天输入框在虚拟键盘弹出时应尽量固定在键盘上方。
- 键盘弹出后，聊天记录应保持最新消息和输入区可见。
- 复杂滑动手势暂不作为核心交互，避免与浏览器返回、系统手势冲突。
- 默认优先竖屏体验；横屏只保证不崩，不作为第一优先级设计。
- 页面底部操作区应考虑 `safe-area-inset-bottom`。

## 11. 动效原则

动效用于表达状态，不做无意义装饰。

可用动效：

- 生命周期变化。
- 骰点结果出现。
- 黑水港咬钩和收竿。
- 溺者之牌翻牌。
- 危险操作确认。
- sheet 打开和关闭。

避免：

- 全屏闪烁。
- 大面积粒子遮挡正文。
- 永久循环强动画。
- 影响输入和阅读的背景动画。

## 12. 轻量验收

默认不做深度测试。

每个阶段只做必要检查：

1. 文档自检：无明显矛盾、无未定义术语。
2. 代码涉及时做 TypeScript / lint 轻量检查。
3. 样板页做少量截图确认。
4. 检查 375px、1440px、2560x1080 三个关键宽度。
5. 检查主内容不再像黑色透明卡片。
6. 检查中文正文 14px-16px 可读。

不主动做：

- 全站 E2E。
- 深度 Playwright。
- 全量视觉回归。
- 生产部署。

## 14. 风险与规避

| 风险 | 表现 | 规避方式 |
| --- | --- | --- |
| image2 图好看但不能用 | 太像海报、细节抢正文 | 先写资产规格卡，只生成 UI texture |
| 页面继续逐页补丁 | 视觉统一但结构仍乱 | 先 IA 和线框，再做样板页 |
| 房间页误改业务 | 权限、生命周期、骰点出问题 | 房间页只动前端结构，遵守契约 |
| 移动端信息堆叠 | PL 找不到聊天和骰点 | 移动端按 PL 主任务重排 |
| 过度黑暗 | 旧版克苏鲁黑幕感回潮 | 明亮档案纸和浅色湿石作为主内容 |
| 过度华丽 | 装饰压过跑团操作 | 背景负责氛围，Surface 负责可读 |
